# Host API Boundary And Commutator Timings

Date: 2026-11-03

This report measures the host `PauliSum` additions from the usability and kernel
campaign (`docs/plans/usability_and_kernel_campaign_plan.md`, slices 2 and 3):

- packed-array I/O (`from_arrays` / `to_arrays`);
- bulk NumPy coefficient conversion in `from_labels`;
- fused `commutator` / `anticommutator`.

## Evidence

```text
benchmark: benchmarks/bench_host_api.py
summaries: docs/benchmarks/data/host_api_2026-11-03/summary_apple_m4_pro.json
           docs/benchmarks/data/host_api_2026-11-03/summary_x86_64.json
per-run reports: private archive (docs/benchmarks/data/**/raw/ is not published)
```

Commands, run 7 times per machine with seed `20261103 + run`. Within each run,
the baseline/candidate order is randomized:

```text
base (main d555868):          python benchmarks/bench_host_api.py --suite boundary --label base --seed <s>
candidate (7c64436 + docs):   python benchmarks/bench_host_api.py --suite all --label cand --seed <s>
summary:                      python benchmarks/bench_host_api.py --summarize <dir> --output <summary>
```

Each run uses 1 warmup and 7 timed repetitions per variant, and variants inside
a case run in a randomized order each repetition. Fused results are checked for
equivalence with the composed products before timing. Every run's loaded
extension matched its checkout's native sources. The git trees were dirty only
because of uncommitted docs (candidate) and the copied benchmark script (base).

| Machine | CPU | Compiler | Python | CPU backend |
| --- | --- | --- | --- | --- |
| Apple Silicon | Apple M4 Pro, 12 cores, macOS arm64 | Apple clang 21.0.0 | 3.12.12 | scalar |
| x86_64 | 26 logical CPUs, Linux 6.8 | GCC 13.3.0 | 3.12.3 | scalar |

Operators are random dense labels with complex normal coefficients.

## Boundary

Medians of the per-run medians. `from_labels` receives a NumPy `complex128`
coefficient array. `from_arrays` receives `uint64` word arrays and `complex128`
coefficients.

| Machine | qubits | terms | from_labels main | from_labels candidate | from_arrays | to_labels | to_arrays |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| M4 Pro | 24 | 1,000,000 | 192.7 ms | 164.5 ms | 0.93 ms | 58.7 ms | 12 us |
| M4 Pro | 100 | 1,000,000 | 592.1 ms | 565.4 ms | 1.16 ms | 133.8 ms | 14 us |
| x86_64 | 24 | 1,000,000 | 302.4 ms | 249.5 ms | 5.03 ms | 315.0 ms | 19 us |
| x86_64 | 100 | 1,000,000 | 805.6 ms | 759.5 ms | 7.50 ms | 1,048.7 ms | 21 us |

At 100,000 terms the ratios are similar. `from_arrays` is 91-439x faster than
`from_labels` there, against 50-486x across every measured size.

- **from_arrays vs from_labels:** 50-486x faster across all sizes, because it
  skips string parsing; the gap widens with width on Apple Silicon.
- **to_arrays:** returns views rather than copies, so it takes microseconds at
  every size.
- **Bulk coefficient conversion:** makes `from_labels` 1.17-1.21x faster at 24
  qubits and 1.05-1.06x at 100 qubits. The remaining cost is label parsing.
- **to_labels:** unchanged within run-to-run movement (-1.4% to +1.9%).

## Commutators

Fused `a.commutator(b)` vs composed `(a @ b - b @ a).simplify()` on two
simplified operators of equal size, with the same comparison for the
anticommutator. Medians over runs:

| Machine | qubits | terms per operand | fused commutator | composed | speedup | anticommutator speedup |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| M4 Pro | 24 | 500 | 8.77 ms | 71.1 ms | 8.1x | 8.2x |
| M4 Pro | 24 | 2,000 | 164 ms | 1,532 ms | 9.3x | 9.4x |
| M4 Pro | 100 | 2,000 | 178 ms | 1,663 ms | 9.3x | 9.2x |
| x86_64 | 24 | 500 | 15.4 ms | 117 ms | 7.6x | 7.5x |
| x86_64 | 24 | 2,000 | 324 ms | 3,022 ms | 9.3x | 9.2x |
| x86_64 | 100 | 2,000 | 420 ms | 3,756 ms | 8.9x | 8.7x |

Random operands make about half of all pairs anticommute; the commutator kept
1,998,683 of 4,000,000 pairs at 24 qubits and 2,000 terms. The fused kernel
generates only those pairs and simplifies once. The composed form generates
every pair twice, simplifies each product, concatenates the two and simplifies
again. That accounts for a gain well beyond the 2x from skipping pairs alone.

## Limitations

- Scalar CPU only; none of these paths has a oneTBB or SIMD variant yet.
- Random dense operators. Structured operators, such as chemistry Hamiltonians
  with many commuting pairs, change the fraction of pairs the commutator keeps.
- The `from_labels` comparison spans two builds, and the other boundary rows
  come from one build. Neither has an unchanged control beyond `to_labels`.
  `to_labels` stayed flat between builds.

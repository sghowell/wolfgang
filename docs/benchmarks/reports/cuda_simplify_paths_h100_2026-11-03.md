# CUDA Simplify Paths On H100

Date: 2026-11-03

This report qualifies the CUDA simplify changes from the usability and kernel
campaign (`docs/plans/usability_and_kernel_campaign_plan.md`, slice 1):

- the CUDA build, broken on `main` since `ee4f95f`, compiles again;
- operators wider than 128 qubits reduce duplicates with a parallel segmented
  `reduce_by_key` instead of a one-thread kernel;
- one- and two-word paths use `stable_sort_by_key`;
- single-term inputs skip sort and reduction;
- every path applies the CPU drop rule to finite coefficients whose magnitude
  exceeds `DBL_MAX`.

Before timing starts, the first output of every variant is checked against CPU
canonical labels and coefficients.

Defaults: 2 warmups and 9 timed repetitions per variant, seed 20261102.
Operators are random dense labels with complex normal coefficients. A
duplicate fraction `d` builds `round(n * (1 - d))` unique strings and fills
the rest by resampling them.

Boundaries:
- **Device-resident** rows time `DevicePauliSum.simplify()` on an operator
  already on the GPU. The call synchronizes and includes output allocation.
- **Transfer-inclusive** rows time `PauliSum.to_device().simplify().to_host()`.
- **CPU rows** are host-in, host-out `PauliSum.simplify()`.

## Generic path (more than 128 qubits)

Within each repetition, the following variants run in a randomized order:

- the parallel path, device-resident and transfer-inclusive;
- the retained serial kernel (`WOLFGANG_CUDA_BENCH_GENERIC_MULTIWORD_REDUCTION=serial_kernel`);
- CPU simplify, the unchanged control.

Benchmark-selector updates happen outside the timed region.

| qubits | terms | dup | parallel (device) | parallel (transfer-incl.) | serial kernel | CPU | vs serial | device vs CPU | transfer vs CPU |
| ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 130 | 4096 | 0.0 | 0.242 ms | 1.29 ms | 3.27 ms | 0.467 ms | 13.5x | 1.93x | 0.36x |
| 130 | 65536 | 0.0 | 0.578 ms | 3.09 ms | 54.3 ms | 11.3 ms | 94x | 19.6x | 3.66x |
| 130 | 65536 | 0.9 | 0.494 ms | 2.28 ms | 57.3 ms | 10.1 ms | 116x | 20.4x | 4.43x |
| 256 | 65536 | 0.0 | 0.580 ms | 3.54 ms | 52.9 ms | 12.3 ms | 91x | 21.3x | 3.48x |
| 1024 | 4096 | 0.9 | 0.651 ms | 1.86 ms | 11.3 ms | 0.798 ms | 17.3x | 1.23x | 0.43x |
| 1024 | 65536 | 0.0 | 0.650 ms | 6.80 ms | 178 ms | 22.5 ms | 273x | 34.7x | 3.32x |
| 1024 | 65536 | 0.9 | 1.02 ms | 4.20 ms | 197 ms | 19.2 ms | 192x | 18.8x | 4.57x |

**Against the serial kernel.** At 65,536 terms the parallel path is 91-273x
faster. At 128 terms it is 1.1-2.0x faster.

**Against CPU.** On data already on the device, CUDA beats CPU from about 4,096
terms. Counting transfers, it wins only at the 65,536-term size (3.3-4.6x). At
4,096 terms and below, the round trip loses to CPU. At 128 terms
device-resident CUDA is 10-29x slower than CPU (0.20-0.40 ms vs 0.008-0.020 ms),
because the per-call GPU floor dominates. A transfer-inclusive call takes about
0.97 ms even for one term.

The full 24-row matrix is in `summary.json`.

## Single-term fast path

The first generic run (`4232c1f`, also in `summary.json`) showed the parallel
path paying 0.21-0.26 ms at one term, about 0.05 ms more than the serial kernel.
With the fast path, one-term device-resident simplify takes 0.027-0.028 ms at
130, 256 and 1024 qubits. The CPU control stayed at 0.001 ms in both runs.

## Specialized paths and stable sort

Seven paired reruns compare baseline `c65553c` (the build fix only) with
candidate `dfd0bf8` (every slice 1 change). The order is randomized per rerun,
and each rerun uses a fresh seed shared by both builds. The baseline checkout is
dirty only because the benchmark script was copied into it. Values are medians
of the per-rerun medians; duplicate fraction 0.5.

| path | qubits | terms | device-resident cand/base | transfer-inclusive cand/base | CPU control cand/base |
| --- | ---: | ---: | ---: | ---: | ---: |
| one-word packed 32-bit key | 24 | 50,000 | 1.001 | 1.003 | 1.000 |
| one-word packed 32-bit key | 24 | 1,000,000 | 0.997 | 1.001 | 1.007 |
| one-word two-mask key | 60 | 50,000 | 1.004 | 0.992 | 1.005 |
| one-word two-mask key | 60 | 1,000,000 | 0.986 | 1.015 | 1.005 |
| two-word key | 100 | 50,000 | 1.002 | 1.011 | 0.997 |
| two-word key | 100 | 1,000,000 | 0.998 | 1.009 | 1.010 |

The GPU ratios span 0.986-1.015, about the spread of the unchanged CPU control
(0.997-1.010). No measured cost is attributable to the stable sort or the
drop-rule change.

At one million terms, the absolute device-resident medians are 1.56 ms (packed
key), 1.85 ms (two-mask key) and 2.52 ms (two words). Transfer-inclusive
medians are 12.5-17.0 ms.

## Correctness and sanitizers

Tests in `tests/test_cuda_generic_simplify.py` cover:

- widths of 130, 256 and 1024 qubits;
- 0, 1, 128 and 4096 terms;
- duplicate fractions 0.0 and 0.9, with cancellation;
- relative thresholds;
- single-term drop rules at 0, 3, 60, 100 and 130 qubits;
- finite coefficients with overflowing magnitude;
- duplicate runs of 24,000 terms that span reduction tiles;
- both reduction strategies.

The CUDA foundation and kernel suites also pass, and full
`WOLFGANG_VALIDATE_CUDA=1 python scripts/validate.py --profile core` passes.

Compute Sanitizer on `tests/test_cuda_generic_simplify.py`:

| Tool | Result |
| --- | --- |
| memcheck (`--leak-check full`) | 0 errors, 0 bytes leaked |
| racecheck | 0 hazards |
| synccheck | 0 errors |
| initcheck | reports only inside CUB's `ReduceByKeyAgent` |

The initcheck reports are reads of decoupled look-back tile state in CUB's
`reduce_by_key`. The baseline build `c65553c`, before any slice 1 change,
produces the same 1,356 reports on its existing one- and two-word paths, so
they predate this slice. The slice adds no Wolfgang kernel reads of
uninitialized memory.

Sanitizer runs print nanobind "leaked instances" notices at interpreter
shutdown. Plain pytest runs of the same tests print none, so the notices come
from shutdown ordering under the sanitizer.

## Interpretation

The generic path was the only CUDA simplify path whose cost grew linearly on
one GPU thread. It now scales like the specialized paths. The remaining cost
for small inputs is per call (allocation, transfers, device discovery and
synchronization), and slice 7 of the campaign targets it.

## Limitations

- One H100 SXM (80 GB HBM3) host and one toolkit (12.8). No A100, Blackwell or
  HIP rows. HIP already used the parallel design but lacks the single-term fast
  path and the overflow drop rule, and was not re-measured.
- Dense random labels only. Structured operators with 130+ qubits were not
  measured.
- Device-resident rows include output allocation and a device synchronize per
  call, so they are not kernel-only times.
- The single-term comparison uses two separate runs, not paired reruns. The CPU
  control did not change between them, and the effect (about 8x) is far larger
  than run-to-run variation.
